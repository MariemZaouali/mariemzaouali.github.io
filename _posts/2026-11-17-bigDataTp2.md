# TP2 : Data Lakehouse avec Apache Hive, Hadoop et Apache Iceberg

> **Objectifs du TP :**
> Au terme de ce laboratoire complet, vous serez capable de :
> - Manipuler l'ensemble des commandes DDL/DML HQL (Hive Query Language) pour administrer, modéliser et requêter des données massives sur HDFS.
> - Comprendre et comparer les formats physiques de stockage (**TextFile, Parquet, ORC**) 
> - Déployer des stratégies de partitionnement (statique, dynamique) et de **Bucketing** pour accélérer les jointures (**Map-side Joins**).
> - Orchestrer un pipeline d'ingestion RDBMS vers le Data Lake à l'aide de **Sqoop** et PostgreSQL.
> - **Moderniser l'architecture vers le paradigme Data Lakehouse** grâce à la brique **Apache Iceberg**.
> - Maîtriser les garanties transactionnelles **ACID**, les **Snapshots**, le **Time Travel**, le **Rollback**, le **Partitionnement Caché (Hidden Partitioning)** et l'**Évolution de Schéma/Partition sans réécriture de données**.

# SECTION 2 : FONDAMENTAUX HIVE – FORMATS, TABLES ET STOCKAGE PHYSIQUE

## 2.1 Row Format et Séparateurs de Champs

Découvrons comment créer une table gérée dont les champs sont délimités par une virgule `,`. Au niveau physique sur HDFS, les données brutes contiennent ces séparateurs.

Exécutez dans Hive CLI :

```sql
CREATE TABLE jobs (
    id INT, 
    title STRING, 
    salary INT, 
    posted TIMESTAMP
) 
ROW FORMAT DELIMITED 
FIELDS TERMINATED BY ',';
```

Vérifiez l'existence de la table dans la base `default` :

```sql
SHOW TABLES;
```

Insérez un premier enregistrement :

```sql
INSERT INTO jobs VALUES (1, 'Data Analyst', 135000, '2016-12-21 15:52:03');
```

Visualisez la ligne insérée :

```sql
SELECT * FROM jobs;
```

Quittez temporairement la console (`quit;`) et examinez le stockage physique sur HDFS. Le répertoire `/user/hive/warehouse` est l'emplacement par défaut :

```bash
hdfs dfs -ls /user/hive/warehouse
hdfs dfs -ls /user/hive/warehouse/jobs
```

Affichez le contenu brut du fichier généré :

```bash
hdfs dfs -cat /user/hive/warehouse/jobs/000000_0
```

> **Observation :** Les chaînes et les timestamps ne comportent pas de guillemets dans HDFS. Les champs sont strictement séparés par des virgules : `1,Data Analyst,135000,2016-12-21 15:52:03`.

Créez maintenant une table délimitée par une tabulation `\t` :

```sql
CREATE TABLE jobs_tsv (
    id INT, 
    title STRING, 
    salary INT, 
    posted TIMESTAMP
) 
ROW FORMAT DELIMITED 
FIELDS TERMINATED BY '\t';

INSERT INTO jobs_tsv VALUES (1, 'Data Analyst', 135000, '2016-12-21 15:52:03');
```

En inspectant `/user/hive/warehouse/jobs_tsv/000000_0`, vous remarquerez le séparateur `\t`. Le délimiteur tabulation est particulièrement recommandé lorsque les champs textuels métier contiennent naturellement des virgules.

## 2.2 Tables Internes (Managed) vs Tables Externes (External)

Par défaut, Hive gère à la fois le **schéma logique** (dans le Metastore) et le **cycle de vie des fichiers physiques** (sur HDFS). Une table `EXTERNAL` permet de décorréler le schéma logique des données brutes : la suppression de la table (`DROP TABLE`) ne supprime que le catalogue, sans détruire les données sur HDFS.

Créez une table externe :

```sql
CREATE EXTERNAL TABLE default.investors (
    name STRING, 
    amount INT, 
    share DECIMAL(4,3)
) 
ROW FORMAT DELIMITED 
FIELDS TERMINATED BY ',';

INSERT INTO default.investors (name, amount, share)
VALUES ('Karim Beguir', 10000, 0.325);

SHOW TABLES;
```

Vérifiez la présence des données dans HDFS :

```bash
hdfs dfs -ls /user/hive/warehouse/investors
```

Supprimez la table externe dans Hive :

```sql
DROP TABLE default.investors;
```

Vérifiez à nouveau le système de fichiers HDFS :

```bash
hdfs dfs -ls /user/hive/warehouse/investors
```

> **Constat majeur :** Le dossier `/user/hive/warehouse/investors` et ses fichiers de données subsistent intégralement !
> Si vous recréez la table avec le même schéma :
> ```sql
> CREATE EXTERNAL TABLE default.investors(name STRING, amount INT, share DECIMAL(4,3));
> SELECT * FROM investors;
> ```
> Toutes les lignes réapparaissent instantanément sans réinsertion.

## 2.3 Formats de Fichiers : TEXTFILE vs PARQUET

Comparons l'impact du format de stockage :

```sql
-- Format texte standard
CREATE TABLE jobs_txt (
    id INT, 
    title STRING, 
    salary INT, 
    posted TIMESTAMP
) 
STORED AS TEXTFILE;

INSERT INTO jobs_txt VALUES (1, 'Data Analyst', 135000, '2016-12-21 15:52:03');

-- Format colonnaire Parquet
CREATE TABLE jobs_parquet (
    id INT, 
    title STRING, 
    salary INT, 
    posted TIMESTAMP
) 
STORED AS PARQUET;

INSERT INTO jobs_parquet VALUES (1, 'Data Analyst', 135000, '2016-12-21 15:52:03');
```

En examinant `/user/hive/warehouse/jobs_txt`, les fichiers sont lisibles en clair (`hdfs dfs -cat ...`).
En examinant `/user/hive/warehouse/jobs_parquet`, le fichier est binaire, compressé et organisé par colonnes avec en-têtes et dictionnaires.

## 2.7 Partitionnement Statique et Dynamique

Le partitionnement segmente physiquement les tables sous forme de sous-répertoires HDFS du type `colonne=valeur`. Cela permet au moteur d'ignorer la lecture de dossiers entiers (**Partition Pruning**).

### A. Téléchargement et Chargement de `customers.csv`

Téléchargez le fichier `customers.csv` depuis l'espace de stockage du cours :
```link
https://drive.google.com/drive/folders/1yHi5gPFu_4999GhdemwRD8ux2mllufU8?usp=drive_link
```

Placez-le dans le conteneur ou copiez-le sur HDFS :

```bash
hdfs dfs -put customers.csv /user/hive/warehouse/customers.csv
```

```sql
CREATE TABLE IF NOT EXISTS customers (
    id_cust INT,
    name STRING,
    country STRING
)
```

Créez la table partitionnée :

```sql
CREATE TABLE customers_by_country (
    id_cust INT, 
    name STRING
)
PARTITIONED BY (country STRING)
ROW FORMAT DELIMITED
FIELDS TERMINATED BY ',';
```

Activez le partitionnement dynamique non strict dans la session Hive :

```sql
SET hive.exec.dynamic.partition.mode=nonstrict;

INSERT OVERWRITE TABLE customers_by_country
```

```bash

```
Chaque pays dispose désormais de son propre dossier (ex: `country=France/`, `country=USA/`).

## 2.8 Bucketing et Optimisation Map-Side Join

Le **Bucketing** (compartimentage) répartit les données en un nombre fixe de fichiers basé sur la fonction de hachage d'une clé (`hash(col) % N`).

### Avantages Majeurs :
1. **Échantillonnage rapide (Sampling) :** Exploration d'un échantillon représentatif sans scanner la totalité de la table.
2. **Map-Side Join :** Si deux tables jointes sont bucketées sur la même clé avec des multiples compatibles de buckets, la jointure est résolue directement en mémoire côté Mapper (**pas de phase Shuffle/Sort, pas de Reducer**), ce qui multiplie les performances par 5 à 10.

Création de la table bucketée en 8 fragments :

```sql
CREATE TABLE customers_bucketed (
    id_cust INT,
    name STRING,
    country STRING
)
CLUSTERED BY (id_cust) INTO 8 BUCKETS
ROW FORMAT DELIMITED
FIELDS TERMINATED BY ',';

SET hive.enforce.bucketing = true;

INSERT INTO TABLE customers_bucketed
SELECT * FROM customers;
```

Extraction d'un échantillon (Bucket 3 sur 8) :

```sql
SELECT * FROM customers_bucketed TABLESAMPLE(BUCKET 3 OUT OF 8);
```

Vérifiez la présence exacte de 8 fichiers de données dans HDFS :

```bash
hdfs dfs -ls /user/hive/warehouse/customers_bucketed
```

## 2.9 Optimisations Avancées : Format ORC, CBO et PPD

Le format **ORC (Optimized Row Columnar)** combine compression par blocs, index intégrés (min/max par stripe) et dictionnaires.

```sql
CREATE TABLE IF NOT EXISTS customers_orc
STORED AS ORC AS
SELECT * FROM customers;
```

### A. Cost-Based Optimizer (CBO)

Le CBO s'appuie sur le moteur Apache Calcite pour construire le plan d'exécution optimal en exploitant la distribution statistique des données :

```sql
SET hive.cbo.enable=true;
SET hive.compute.query.using.stats=true;

ANALYZE TABLE customers_orc COMPUTE STATISTICS FOR COLUMNS;
```

### B. Predicate Pushdown (PPD)

Le PPD pousse les prédicats de filtrage (`WHERE`) directement au niveau du lecteur de stockage ORC. Les blocs dont les statistiques min/max excluent la valeur recherchée sont éliminés avant même toute décompression ou chargement en mémoire.

Activez les propriétés PPD :

```sql
SET hive.optimize.ppd = true;
SET hive.optimize.ppd.storage = true;
SET hive.orc.splits.include.file.footer = true;
SET hive.optimize.index.filter = true;
```

Inspectez le plan d'exécution avec `EXPLAIN` :

```sql
EXPLAIN SELECT * FROM customers_orc WHERE country = 'France';
```

Vérifiez dans la sortie :
```text
TableScan
  alias: customers_orc
  PushedPredicate: country = 'France'
```
Le scan physique saute tous les stripes ORC ne contenant aucun client français.

# SECTION 4 : LA BRIQUE APACHE ICEBERG & ARCHITECTURE DATA LAKEHOUSE

> **Pourquoi moderniser vers Apache Iceberg ?**
> Les tables Hive traditionnelles présentent des limites architecturales majeures en entreprise :
> - **Absence de transactions ACID complètes :** Risque de lectures corrompues (dirty reads) pendant les écritures concurrentes.
> - **Partition Drift :** Si une colonne de partition change ou si un développeur oublie la clause de partition dans un filtre, le moteur scanne l'intégralité du Data Lake.
> - **Lenteur des métadonnées :** Le Metastore Hive doit lister des milliers de répertoires HDFS (`listStatus`), ce qui sature le NameNode.
> - **Impossibilité de versionner :** Pas de Time Travel natif, pas de rollback instantané en cas d'erreur d'ingestion.
> 
> **Apache Iceberg** résout ces problématiques en introduisant une couche de format de table ouverte avec un arbre de métadonnées immuable sur le stockage objet/HDFS.

## 4.1 Anatomie d'une Table Iceberg : Snapshots et Métadonnées

Créons une table Iceberg version 2 et étudions comment Iceberg trace chaque commit.

```sql
CREATE TABLE lab3.jobs_ice (
    id INT, 
    title STRING, 
    salary INT, 
    posted TIMESTAMP
)
STORED BY ICEBERG
TBLPROPERTIES ('format-version'='2');

-- Premier commit (création du premier Snapshot)
INSERT INTO lab3.jobs_ice 
VALUES (1, 'Data Analyst', 135000, '2016-12-21 15:52:03');

-- Deuxième commit (création du second Snapshot)
INSERT INTO lab3.jobs_ice 
VALUES (2, 'Data Engineer', 150000, '2017-03-02 09:10:00');
```

### A. Inspection des Snapshots

Interrogez la table système de métadonnées `.snapshots` :

```sql
SELECT snapshot_id, parent_id, committed_at, operation 
FROM lab3.jobs_ice.snapshots 
ORDER BY committed_at;
```

> **Observation :** Deux `INSERT` distincts génèrent deux snapshots consécutifs reliés hiérarchiquement (`parent_id`). Chaque snapshot représente un état logique complet et figé de la table à un instant T.

### B. Inspection Physique : Arbre de Métadonnées sur HDFS

Quittez Hive et inspectez l'organisation du dossier sous HDFS :

```bash
hdfs dfs -ls /user/hive/warehouse/lab3.db/jobs_ice
hdfs dfs -ls /user/hive/warehouse/lab3.db/jobs_ice/metadata
hdfs dfs -ls /user/hive/warehouse/lab3.db/jobs_ice/data
```

```
Table jobs_ice/
├── data/
│   ├── 00000-0-data-xxx.parquet          <-- Fichier écrit lors du commit 1
│   └── 00001-0-data-yyy.parquet          <-- Fichier écrit lors du commit 2
└── metadata/
    ├── v1.metadata.json                  <-- Schéma initial
    ├── v2.metadata.json                  <-- Pointeur Snapshot 1
    ├── v3.metadata.json                  <-- Pointeur Snapshot 2 (courant)
    ├── snap-12345-1-manifest-list.avro   <-- Liste des manifests du snapshot
    └── manifest-abcde.avro               <-- Fichiers de données et stats min/max
```

### C. Rôles Respectifs des Composants

| Composant | Rôle Précis | Ce qu'il gère |
| :--- | :--- | :--- |
| **HDFS** | Stockage physique brut | Fichiers Parquet et fichiers de métadonnées Avro/JSON |
| **Hive Metastore** | Catalogue logique / Pointeur atomique | Pointeur vers le fichier de métadonnées courant (`v3.metadata.json`) |
| **Apache Iceberg** | Format de table & Gestion d'état | Arbre de métadonnées, snapshots, partitions cachées, Field IDs |
| **Hive / Tez** | Moteur de traitement SQL distribué | Analyse de requête, optimisation, exécution des tâches de lecture/écriture |

> **Question de Réflexion (Catalogue Indisponible) :**
> *Si le Metastore PostgreSQL devient indisponible, les données sont-elles perdues ?*
> **Réponse :** Non. Les fichiers de données et l'intégralité de l'historique des snapshots restent intacts sur HDFS. Cependant, les moteurs SQL ne peuvent plus résoudre le nom logique `lab3.jobs_ice` vers le fichier de métadonnées courant. L'accès opérationnel est suspendu tant que le catalogue n'est pas restauré.

### 2.2 Conversion In-Place (Sans Réécriture de Données)

```sql
SELECT * FROM lab2_big_data.customers_orc.snapshots;
```

> **Point Technique Clé :** La conversion in-place n'a déplacé aucun octet de données. Iceberg a simplement scanné les fichiers ORC existants et généré le graphe de métadonnées Avro/JSON correspondant.

### 2.3 Comparaison : Snapshot / Add Files vs CTAS

| Méthode | Mécanisme | Coût E/S & Réécriture | Cas d'Usage Typique |
| :--- | :--- | :--- | :--- |
| **CTAS** | Lecture source + réécriture complète en Parquet Iceberg | Élevé (réécriture 100%) | Source CSV/TextFile ou changement de schéma/types |
| **In-place Convert** | Adoption des fichiers ORC/Parquet existants par métadonnées | Nul (zéro réécriture) | Tables existantes propres au bon format |
| **Snapshot Procedure** | Adoption d'un jeu de fichiers externes via Spark/Iceberg API | Quasi-nul | Migration de répertoires externes volumineux |
| **Add Files** | Ajout incrémental de fichiers compatibles à une table Iceberg | Nul | Ingestion batch de micro-lots externes |

```sql
WITH eligible AS (
```

### 3.4 Analyse du Partitionnement Caché (Hidden Partitioning)

> **Qu'apporte le Partitionnement Caché d'Iceberg par rapport à Hive ?**
> - **Dans Hive standard :** L'utilisateur devait créer une colonne artificielle `order_date STRING`. Les requêtes devaient obligatoirement filtrer sur `WHERE order_date = '2024-02-01'` pour bénéficier du pruning. Si un analyste écrivait `WHERE order_ts >= '2024-02-01'`, Hive lisait TOUTE la table !
> - **Dans Apache Iceberg :** La table n'expose pas de colonne redondante. L'utilisateur filtre directement sur sa colonne métier `order_ts` :
>   ```sql
>   SELECT * FROM lab3.orders_silver 
>   WHERE order_ts BETWEEN '2024-02-01 00:00:00' AND '2024-02-01 23:59:59';
>   ```
>   Iceberg calcule la relation mathématique `days(order_ts)` et élague automatiquement les fichiers non concernés sans aucune intervention de l'utilisateur.

Vérifiez le plan d'exécution :

```sql

```

## 4.4 Évolution de Schéma et de Partition (Zero-Copy)

Dans un Data Lake traditionnel, renommer une colonne ou changer de partitionnement imposait la réécriture complète de téraoctets de données. Iceberg révolutionne cette maintenance grâce aux **Field IDs**.

### A. Évolution du Schéma (Schema Evolution)

```sql
-- 1. Ajout d'une colonne (valeur par défaut NULL pour les lignes historiques)
ALTER TABLE lab3.orders_silver ADD COLUMNS (delivery_zone STRING);

-- 2. Renommage d'une colonne sans altérer les fichiers Parquet
ALTER TABLE lab3.orders_silver CHANGE COLUMN discount discount_rate FLOAT;

-- 3. Élargissement de type sécurisé (INT vers BIGINT)
ALTER TABLE lab3.orders_silver CHANGE COLUMN price price BIGINT;
```

Vérifiez le nouveau schéma :

```sql
DESCRIBE lab3.orders_silver;
```

> **Mécanisme des Field IDs :**
> Iceberg attribue à chaque colonne un identifiant entier immuable unique (ex: `price -> Field ID 3`).
> - Lors d'un renommage (`discount` vers `discount_rate`), seul le JSON de métadonnées est modifié : le Field ID reste inchangé. À la lecture, Iceberg fait le lien direct.
> - Si une colonne est supprimée puis recréée avec le même nom, elle reçoit un NOUVEL ID, éliminant tout risque de collision ou de lecture de données zombies.

### B. Évolution de la Spécification de Partition (Partition Evolution)

Supposons que le volume de données augmente et que le partitionnement journalier produise trop de petits fichiers. Nous décidons de passer à un partitionnement mensuel :

```sql
ALTER TABLE lab3.orders_silver 
SET PARTITION SPEC (months(order_ts), bucket(8, restaurant_id));
```

> **Comportement Révolutionnaire :**
> Les anciens fichiers Parquet conservent leur partitionnement par jour. Les nouvelles insertions appliqueront le partitionnement par mois. Iceberg unifie les deux générations de partitions dans un plan de requête unique et transparent !

### D. Restauration Atomique par Rollback

Rétablissons la table à son état d'origine en annulant l'opération `DELETE` :

Pour libérer de l'espace disque et respecter les contraintes de gouvernance, nous expirons les snapshots antérieurs à une date donnée :

| Opération | Effet sur l'État Courant | Effet sur l'Historique / Fichiers |
| :--- | :--- | :--- |
| **DELETE** | Supprime des lignes de l'état actif | Conserve les lignes dans les snapshots passés |
| **ROLLBACK** | Rétablit un snapshot antérieur comme état actif | Ne détruit pas les données (ajoute un commit) |
| **EXPIRE SNAPSHOTS** | Inchangé | Supprime définitivement les snapshots périmés et les fichiers orphelins sur HDFS |

## 4.6 Branches, Tags et Pattern WAP (Write-Audit-Publish)

Le pattern **WAP (Write-Audit-Publish)** permet d'isoler les écritures de données dans une branche dédiée, de valider des tests de qualité automatisés, puis de promouvoir les données validées en production de manière atomique.

```
                    +------------------------------------+
                    |  Branche 'audit' (Ingestion lot)  |
                    |  --> Contrôle Qualité (Prix, IDs)  |
                    +------------------------------------+
                                      |
                     Fast-Forward     v  (Si Qualité OK)
main (Production) ==========================================> [ TAG: release_v1 ]
```

### 1. Création d'une Branche d'Audit

```sql
ALTER TABLE lab3.orders_silver CREATE BRANCH audit;

-- Visualisation des références actives (branches et tags)
SELECT name, type, snapshot_id FROM lab3.orders_silver.refs;
```

### 2. Écriture Isolée sur la Branche

Insérons un lot de test uniquement sur la branche `audit` :

```sql
INSERT INTO lab3.orders_silver.branch_audit VALUES (
    CAST('2024-02-01 10:00:00' AS TIMESTAMP),
    'DELIVERED', 
    320, 
    0.0,
    'audit-0001', 
    'd2', 
    'u2', 
    'r2',
    'Zone-Nord'
);

-- Vérification de l'isolation :
SELECT COUNT(*) FROM lab3.orders_silver.branch_audit;
SELECT COUNT(*) FROM lab3.orders_silver; -- La table de prod 'main' n'a pas bougé !
```

### 3. Contrôles Qualité Automatisés (Audit Phase)

Avant de publier, nous vérifions l'absence d'anomalies sur la branche :

```sql
-- Règle 1 : Unicité stricte des identifiants
SELECT id, COUNT(*) AS doublons
FROM lab3.orders_silver.branch_audit
GROUP BY id 
HAVING COUNT(*) > 1;

-- Règle 2 : Conformité des montants
SELECT COUNT(*) AS prix_invalides
FROM lab3.orders_silver.branch_audit
WHERE price <= 0;

-- Règle 3 : Validité des horodatages
SELECT COUNT(*) AS dates_invalides
FROM lab3.orders_silver.branch_audit
WHERE order_ts IS NULL;
```

### 4. Publication par Fast-Forward et Pose de Tag

Si tous les indicateurs sont au vert (0 anomalies), nous publions atomiquement :

```sql
-- Promotion de la branche audit vers main
ALTER TABLE lab3.orders_silver EXECUTE FAST-FORWARD 'main' 'audit';

-- Pose d'un tag immuable de versionnage
ALTER TABLE lab3.orders_silver CREATE TAG release_validated;

SELECT name, type, snapshot_id FROM lab3.orders_silver.refs;
```
La table principale `lab3.orders_silver` contient désormais les nouvelles données validées.

# SECTION 5 : PROJETS D'INGÉNIERIE & DÉFIS AVANCÉS

## Défi A : Performance, Compaction et Gestion des Petits Fichiers

L'arrivée continue de micro-batches d'ingestion crée une fragmentation en nombreux petits fichiers (**Small Files Problem**), ce qui dégrade les temps de réponse analytiques.

### Action Corrective : Compaction Iceberg
Iceberg regroupe automatiquement les petits fichiers en gros fichiers optimisés (128 Mo / 512 Mo) sans interrompre les lectures en cours :

```sql
-- Déclenchement de la réécriture compactée des fichiers
ALTER TABLE lab3.orders_silver COMPACT 'major';
-- Ou selon la version Hive/Iceberg :
OPTIMIZE TABLE lab3.orders_silver REWRITE DATA;
```

Vérifiez la consolidation des fichiers dans la table système `.files` :

```sql
SELECT file_path, file_format, record_count, file_size_in_bytes 
FROM lab3.orders_silver.files;
```

## Défi B : Fiabilité et Ingestion Idempotente via `MERGE INTO`

Pour éviter la duplication de lignes lors de rejeux de pipelines en échec, nous implémentons une stratégie d'**Upsert** idempotent :

```sql
-- Création d'une table de staging pour le nouveau lot entrant
CREATE TABLE IF NOT EXISTS lab3.orders_batch LIKE lab3.orders_silver;

-- Modèle de requête MERGE INTO idempotent
MERGE INTO lab3.orders_silver AS t
USING lab3.orders_batch AS s
ON t.id = s.id
WHEN MATCHED THEN UPDATE SET
    order_ts = s.order_ts,
    status = s.status,
    price = s.price,
    discount_rate = s.discount_rate,
    driver_id = s.driver_id,
    user_id = s.user_id,
    restaurant_id = s.restaurant_id,
    delivery_zone = s.delivery_zone
WHEN NOT MATCHED THEN INSERT VALUES (
    s.order_ts, s.status, s.price, s.discount_rate,
    s.id, s.driver_id, s.user_id, s.restaurant_id, s.delivery_zone
);
```

## Défi C : Conformité RGPD et Historisation Temporelle (SCD Type 2)

### 1. Table d'Historisation SCD Type 2 pour les Restaurants
Pour tracer l'historique des modifications d'adresses des restaurants dans le temps :

```sql
CREATE TABLE lab3.restaurants_history (
    restaurant_id STRING,
    restaurant_name STRING,
    address STRING,
    valid_from TIMESTAMP,
    valid_to TIMESTAMP,
    is_current BOOLEAN
) STORED BY ICEBERG;
```

Lorsqu'un restaurant déménage :
1. On met à jour la ligne active : `SET valid_to = CURRENT_TIMESTAMP(), is_current = FALSE WHERE restaurant_id = '...' AND is_current = TRUE`.
2. On insère la nouvelle version : `INSERT INTO ... VALUES (..., CURRENT_TIMESTAMP(), '9999-12-31', TRUE)`.

### 2. Droit à l'Oubli (RGPD) dans un Lakehouse
*Une requête `DELETE FROM orders_silver WHERE user_id = 'U123'` suffit-elle pour respecter le RGPD ?*
**Réponse d'Ingénierie :** **Non !** Les données de l'utilisateur continuent d'exister dans les snapshots historiques antérieurs (consultables via Time Travel). Pour une conformité légale complète, le protocole exige :
1. Exécuter le `DELETE` sur la table courante.
2. Purger les snapshots historiques contenant l'information (`EXECUTE expire_snapshots`).
3. Déclencher le nettoyage des fichiers orphelins non référencés (`remove_orphan_files`).

# SECTION 6 : QUESTIONS DE SOUTENANCE & GUIDE D'ÉVALUATION

| Question de Soutenance | Réponse Attendue & Justification Technique |
| :--- | :--- |
| **Que voit un lecteur pendant une opération `INSERT` ou `MERGE` en cours ?** | Le lecteur bénéficie d'une isolation Snapshot (ACID). Il ne voit que le dernier état cohérent validé. Les fichiers temporaires en cours d'écriture sont invisibles tant que le commit n'a pas publié un nouveau snapshot. |
| **Pourquoi ne faut-il jamais supprimer manuellement des fichiers avec `hdfs dfs -rm` ?** | Les fichiers physiques sont référencés par l'arbre de manifests Avro. Une suppression manuelle corrompt l'intégrité de la table, casse le Time Travel et génère des exceptions `FileNotFoundException`. Il faut utiliser `expire_snapshots`. |
| **Pourquoi préférer `bucket(8, restaurant_id)` plutôt qu'un partitionnement direct par `restaurant_id` ?** | `restaurant_id` a une cardinalité élevée. Un partitionnement classique créerait des milliers de sous-répertoires contenant chacun quelques kilo-octets, saturant la mémoire du NameNode. Le bucketing borne strictement le nombre de fichiers à 8 par tranche. |
| **Quelle est la différence fondamentale entre `DELETE`, `ROLLBACK` et `EXPIRE SNAPSHOTS` ?** | `DELETE` est une mise à jour logique publiant un nouvel état sans les lignes ciblées. `ROLLBACK` déplace le pointeur d'état courant vers un snapshot antérieur. `EXPIRE SNAPSHOTS` détruit définitivement les références historiques et libère le stockage physique. |
| **Que devient un lot écrit sur une branche `audit` si la branche est supprimée avant `FAST-FORWARD` ?** | Le lot n'a jamais été publié sur `main`. Dès la suppression de la branche (`DROP BRANCH`), ses snapshots ne sont plus protégés par aucune référence et seront automatiquement purgés lors du prochain cycle d'expiration. |
